  对一处改动做质量评审：逻辑对不对、是否安全、真实负载下撑不撑得住、有风险逻辑有没有测试、够不够快、每一行是否都必要。
  评审会读取改动触及的代码而不只是 diff，每条发现都用大白话解释清楚。
  当用户说"帮我 review""审查一下这段改动""看看这个 PR""是不是过度设计了""代码审查"时使用，也可直接调用 ponytail:ponytail-review。

像那个"代码半夜炸了会被电话叫醒"的资深开发者一样评审一处改动。

重要性顺序：正确 → 安全 → 真实负载下站得住 → 有测试 → 快 → 精简。精简依然重要：多出来的每一行都要有人读、有人测、以后有人修。这是用户主动要的报告，所以给全。

## 1. 先搞清楚上下文

- **评审用户指定的对象**：未提交或已暂存的改动、某个分支、一个 PR 链接，或者指定文件。用户没指定时，评未提交的改动；没有未提交改动就评最后一次提交。
- **先读 diff，再读它触及的代码**：每个被改函数的调用方、它调用的函数、相关测试、README。
- **追踪真实数据流**：数据从哪进来、存到哪、往哪去。
- 改动可以弄坏它没碰的代码。函数签名、返回值或行为变了，就 grep 所有调用方。
- **在仓库里找到预期负载**（README、部署配置）：一个人跑脚本，还是很多用户和进程同时跑。按那个尺度判断，并**说明你假设的负载**。

## 2. 查这些

1. **Bug**：结果算错、崩溃、漏掉的边界情况（空值、零、最后一项、四舍五入、时区）、被改动弄坏的调用方、只在一个调用方打了补丁而共享函数仍然是坏的。
2. **风险**：安全漏洞（注入、弱随机、密钥、对用户输入缺少校验）、数据丢失（错误被吞、写入顺序错、没有事务）。
3. **规模**：一个人用没事、多人就错的写法：check-then-write 竞态、每个进程都在重复做同一件事、内存或列表只增不减、每个元素一次查询、大输入上的 O(n^2)、必须共享却存在各进程本地的状态。
4. **缺失的测试**：有风险的新逻辑（分支、解析器、金额、安全、数据写入、bug 修复）没有一个"坏了就会红"的测试。要一个好测试，不要覆盖率。
5. **速度**：明显的变慢是问题。小的优化（热循环里重复做的功）算建议——但有些软件每一毫秒都要算。
6. **精简**：本不该存在或本该更小的代码。
   - **删**：死代码、没人用的选项、投机性功能
   - **复用**：仓库里已经有这个 helper（把路径写出来）
   - **标准库/原生**：标准库或平台已经能做；为几行代码新增一个依赖
   - **YAGNI**：只有一个实现的抽象、没人设置的配置
   - **合并**：近似复制、必须一起改的代码
   - **拆分**：一个函数干了好几件不相关的事，所以难读难测。按职责拆，**绝不按行数拆**，也绝不拆出只为让函数变短而存在的 helper。

## 3. 报告前先自查

- 每条发现都要有一个具体场景：「这个输入或这种情况会得到这个错误结果」。没有场景就不是发现。
- 重读相关行确认：调用方真的存在吗？那个值真的可能为空吗？这段代码真的没人用吗？
- 标了 `shortcut:`（旧写法 `ponytail:`）并写明上限的注释是一个**已做的决定**，不是发现——除非预期负载已经越过它的上限。
- 给出能生效的最小修复。**优先选删代码的修复。** 绝不为了解决问题去加层次、框架或配置。
- 不写风格偏好，不写"可以考虑"，不写含糊的担心。

## 4. 输出格式

用简单直白的话：短句、常用词。专业术语第一次出现时解释一下。读者可能从没见过这份代码。

先写 `这次改动做了什么：` 两三句话，并说明你假设的负载。

然后分三组列出发现，空组跳过：

- **必修**：bug、安全问题、数据丢失、在预期负载下会崩。
- **建议修**：有风险但没测试的代码、真实的慢、重复代码、职责混杂的函数、本不该存在的代码。
- **可选优化**：小的提速、更短的写法。

三组统一编号，这样用户可以说"修 2 和 5"。每条发现包含四个部分，每部分一到两句：

```
2. **订单记到了错误的日期**（`billing/close_day.py:L40-52`）
   - **这是什么**：这个任务每天午夜关账，并结算当天所有订单。
   - **问题**：它用服务器时钟取「今天」，而服务器时钟是 UTC。柏林时间 00:30 下的单会被算到前一天。
   - **怎么修**：用店铺所在时区算一次日期：
     `datetime.now(ZoneInfo("Europe/Berlin")).date()`。一行，其他什么都不用动。
   - **不修会怎样**：晚到的订单日期不对，只能靠会计手工调账。
```

结尾写：

- `结论：可以合入。` 或 `结论：先修 1 和 3。`
- `可删代码：约 -N 行。`（有精简类发现时才写）
- `未检查：` 一行，写有什么重要的东西你没来得及查。

什么都没发现时：写 `这次改动做了什么：`，然后 `没问题，可以合入。`，再用一行说明你检查了什么。

**只列发现，不改任何代码。**
